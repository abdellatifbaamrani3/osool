# 28 — Performance, Core Web Vitals, and Arabic SEO

Speed is a conversion feature and a media-cost feature. Paid traffic lands in the Snapchat and
TikTok in-app browsers on cellular Android — the most hostile environment for a slow site. Every
second of delay is money spent on impressions that never see the page.

---

## 1. Performance budgets

Measured on **mobile, 4G, mid-tier Android, p75 real users** — not on a desktop Lighthouse run.

| Metric | Target | Hard fail |
|---|---|---|
| LCP | ≤ 2.0s | > 2.5s |
| INP | ≤ 150ms | > 200ms |
| CLS | ≤ 0.02 | > 0.1 |
| TTFB | ≤ 400ms | > 800ms |
| First-load JS (home) | ≤ 120KB gz | > 160KB |
| First-load JS (product page) | ≤ 160KB gz | > 200KB |
| Total page weight (product) | ≤ 900KB | > 1.4MB |
| Lighthouse mobile performance | ≥ 90 | < 80 |
| Fonts | ≤ 2 families, ≤ 60KB total | — |

CLS target is deliberately stricter than Google's 0.1 threshold. A price or CTA that moves under
her thumb mid-tap is a lost order, not just a metric.

---

## 2. LCP

The LCP element is the **hero image** on home and the **main gallery image** on product pages.

- `priority` + `fetchPriority="high"`, never lazy-loaded
- Exact `width`/`height` or `aspect-ratio` so the box is reserved before load
- AVIF with WebP fallback, `quality={80}`
- `sizes` always specified: `sizes="(max-width: 1024px) 100vw, 50vw"`
- Served from the same origin (Next.js image optimiser) so there is no extra DNS/TLS handshake
- **No scroll-reveal animation on the hero.** An animated LCP element defers the paint that
  actually counts
- Preload the font used by the H1

## 3. CLS

The four causes of layout shift in this project, and their fixes:

| Cause | Fix |
|---|---|
| Images without reserved space | `aspect-ratio` on every image container, including `PlaceholderImage` |
| Font swap | `next/font` with `adjustFontFallback: true` so fallback metrics match |
| Announcement bar / sticky ATC appearing | Reserve height, or animate with `transform` only (never affecting layout) |
| Client-fetched content (reviews) | Skeletons with the exact final dimensions |

Rule: **animate only `transform` and `opacity`.** Never `width`, `height`, `top`, or `left`
(`10` §6).

## 4. INP

- Pixels deferred until after interaction/idle (`23` §3) — the single biggest INP win available
- No heavy synchronous work in event handlers; the offer-selector change must be a state update, nothing more
- `next/dynamic` for the lightbox, comparison table, and review filters
- Debounce the partial-lead capture (1.5s) so it does not fire on every keystroke
- Passive scroll listeners; use `IntersectionObserver` for the sticky ATC rather than a scroll handler
- No `localStorage` writes on every render — Zustand's `persist` already batches

## 5. Loading strategy

| Resource | Strategy |
|---|---|
| Product/home HTML | Static + ISR — served from cache, near-zero TTFB |
| Fonts | Self-hosted via `next/font`, `display: swap`, Arabic subset, `Aref Ruqaa` subset to 4 glyphs |
| LCP image | `priority` |
| Below-fold images | `loading="lazy"` |
| Pixels | Deferred (`23` §3) |
| Third-party embeds | None. No YouTube iframes, no chat widgets, no review-platform scripts. |
| Icons | Tree-shaken from `lucide-react` — verify no full-library import in the bundle analyser |

- `preconnect` / `dns-prefetch`: `api.osool.shop`, `connect.facebook.net`, `analytics.tiktok.com`, `sc-static.net`
- Wire up `@next/bundle-analyzer` and check it before every release. Bundle regressions are silent.

## 6. Arabic SEO

Paid traffic is the primary channel, but organic Arabic search for hair-loss terms is meaningful
and free. The cost of doing this correctly is a few hours.

### 6.1 Fundamentals

- `<html lang="ar" dir="rtl">` — server-rendered (`09` §5)
- Canonical URL on every page, apex domain, no trailing slash
- `www.osool.shop` → 301 → `osool.shop`
- Latin slugs (`09` §2) — Arabic slugs percent-encode badly and break in in-app browsers
- Real, static-rendered content — the product page's 4,000 words of Arabic are a genuine SEO asset
- One `h1` per page, sequential heading levels
- Meaningful Arabic `alt` on every content image
- `sitemap.ts` and `robots.ts` generated by Next.js
- `/thank-you/*` is `noindex, nofollow`

### 6.2 Target keywords

| Page | Primary | Secondary |
|---|---|---|
| Home | تساقط الشعر عند النساء | أسباب تساقط الشعر، علاج تساقط الشعر للنساء السعودية |
| Serum | سيروم لتساقط الشعر | ريدنسل، سيروم كثافة الشعر، فراغات الشعر |
| Tonic | حديد لتساقط الشعر | نقص الحديد وتساقط الشعر، فيريتين، مكمل حديد للشعر |
| Exfoliant | مقشر فروة الرأس | قشرة الشعر، حكة فروة الرأس، تراكمات الفروة |
| Collection | منتجات تساقط الشعر | العناية بفروة الرأس |

Note that some high-volume keywords use words we **cannot** use in our own claims (e.g. «علاج»).
Use them in *research* to understand intent, and in page copy only in non-claim contexts (e.g. a
FAQ question phrased as she would ask it, answered within our approved language — `07` §4).

### 6.3 Metadata

```ts
// app/products/[slug]/page.tsx
export async function generateMetadata({ params }): Promise<Metadata> {
  const p = await getProduct(params.slug);
  return {
    title: `${p.name_ar} | أصول`,
    description: `${p.subtitle_ar} — ${p.hook_ar}. دفع عند الاستلام، توصيل لكل السعودية.`,
    alternates: { canonical: `/products/${p.slug}` },
    openGraph: {
      title: `${p.name_ar} | أصول`,
      description: p.subtitle_ar,
      url: `/products/${p.slug}`,
      siteName: 'أصول',
      locale: 'ar_SA',
      type: 'website',
      images: [{ url: p.images[0].url, width: 1200, height: 630, alt: p.images[0].alt_ar }],
    },
    twitter: { card: 'summary_large_image' },
  };
}
```

Title guidance: ≤ 60 characters, Arabic counts as one character per glyph in Google's pixel-width
calculation but renders wider — keep titles short. Description ≤ 155 characters, and **include the
COD promise**, because it materially improves click-through in this market.

### 6.4 Structured data (JSON-LD)

| Page | Schema |
|---|---|
| All | `Organization` (name in Arabic + English, logo, `contactPoint` with the WhatsApp number, `sameAs` socials) |
| Home | `WebSite` |
| Product | `Product` with `offers` as an `AggregateOffer` (`lowPrice: 199`, `highPrice: 349`, `priceCurrency: "SAR"`, `availability`), plus `aggregateRating` **only when real reviews exist** |
| Product, Home, FAQ | `FAQPage` |
| Product | `BreadcrumbList` |
| Collection | `ItemList` |

> **Compliance warning on `aggregateRating`:** never emit it with seeded review data. Marking up
> fabricated ratings is a Google structured-data violation *and* a misleading-advertising issue
> under E-Commerce Law Article 11 (`07` §6). Gate it on `rating_count > 0 AND NOT is_seed`.

Also: do not put any banned claim word (`07` §3) inside `description` or JSON-LD. Structured data
is crawled and quoted.

### 6.5 Content SEO

- The three-cause model is the natural pillar-content topic. If a blog is ever added, that is the hub.
- FAQ questions should be phrased exactly as she would type them into Google, in dialect.
- Internal linking per `09` §7 — every page links deeper.
- Product pages carry genuine depth (mechanism, ingredients, evidence, timeline), which is what
  actually ranks for Arabic health-adjacent queries.

## 7. Image optimisation

| Setting | Value |
|---|---|
| Formats | AVIF, WebP fallback |
| Quality | 80 |
| `deviceSizes` | `[390, 640, 750, 828, 1080, 1200, 1920]` |
| Max source dimension | 2000px — larger is wasted bytes |
| Product images | 1:1, 1200×1200 source |
| Hero | 4:5 mobile (1080×1350), 16:9 desktop (1920×1080) |
| Review photos | 1:1, 400×400 |
| OG image | 1200×630 |

Compress source assets before they enter the repo. `next/image` optimises delivery, not the
original file — a 6MB source JPEG still costs build time and repo weight.

## 8. Monitoring

- **Vercel Speed Insights or a `web-vitals` beacon** posting to the backend, so we measure real
  Saudi users on real devices rather than a synthetic lab run from Europe
- Track LCP/INP/CLS segmented by: page type, device, and **referrer** (Snapchat in-app vs TikTok
  in-app vs Chrome). These three environments perform differently and an average hides the problem
- Alert if p75 LCP exceeds 2.5s for more than an hour
- Re-run Lighthouse mobile before every release; treat a drop below 80 as a release blocker

## 9. Pre-launch performance checklist

- [ ] Lighthouse mobile ≥ 90 on home, collection, and all 3 product pages
- [ ] LCP ≤ 2.0s on a real mid-tier Android on cellular
- [ ] CLS ≤ 0.02 — verified by scrolling the full product page and watching the layout-shift overlay
- [ ] First-load JS within budget on every route (bundle analyser)
- [ ] No pixel loads before first interaction (check the network waterfall)
- [ ] All images have reserved dimensions and Arabic alt text
- [ ] Fonts subset; only two families load
- [ ] No third-party scripts other than the three pixels
- [ ] `sitemap.xml` and `robots.txt` resolve and list the right pages
- [ ] Canonical tags correct on every page; `www` redirects to apex
- [ ] JSON-LD validates in Google's Rich Results Test
- [ ] `aggregateRating` **absent** while reviews are seeded
- [ ] Tested inside the Snapchat and TikTok in-app browsers on a real phone
